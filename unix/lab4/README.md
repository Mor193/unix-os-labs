## Описание проекта

Микросервисный конвейер пакетной обработки файлов, реализованный на C++17 и развёртываемый с помощью Docker Compose. Входные файлы помещаются в каталог `inbox/` на хосте, распределяются через брокер сообщений между репликами воркеров, обрабатываются через общий том и сохраняются в результирующий каталог.


Сервис состоит из контейнеров трёх типов, объединённых в изолированную сеть `app_net` (`bridge`):

1. **`broker` (`redis:7.4-alpine`)** — центральный брокер сообщений. Хранит очередь задач `tasks`, очередь готовых отчётов `results` и множество `seen_files` для исключения повторной обработки. Обеспечивает балансировку нагрузки между воркерами и их подключение без перенастройки управляющего контейнера.
2. **`controller` (`fileproc-controller:1.0`)** — управляющий контейнер (1 экземпляр). Отслеживает новые файлы в смонтированном каталоге `/inbox` (только чтение), копирует их в общий Docker-том `shared_data` (`/data/in`), отправляет имена файлов в очередь `tasks` и выводит в stdout отчёты из очереди `results`.
3. **`worker` (`fileproc-worker:1.0`)** — тиражируемый контейнер-работник (по умолчанию 3 реплики из одного образа). Ожидает задачи блокирующей операцией `BLPOP`, обрабатывает файл из `/data/in` (перевод содержимого в верхний регистр, подсчёт числа строк и 64-битного хеша FNV-1a), сохраняет результат в `/data/out` и отправляет в `results` отчёт со своим идентификатором контейнера (`hostname`).

## Особенности реализации

* **Работа с файлами и памятью:** чтение/запись реализованы через системные вызовы `open()`, `read()`, `write()`, `close()`; в воркере входной файл отображается в адресное пространство процесса через `mmap(..., PROT_READ, MAP_PRIVATE, ...)`.
* **Штатное завершение процессов:** приложения запускаются как `PID 1` через exec-форму `ENTRYPOINT`; сигналы `SIGTERM` и `SIGINT` перехватываются через `sigaction()` с установкой флага `volatile sig_atomic_t`, позволяя завершить текущую задачу и закрыть соединение с брокером.
* **Контейнеризация и ресурсы:** для всех базовых и локальных образов заданы явные теги вместо `latest`; для каждого сервиса определены лимиты CPU (`0.50`) и памяти (`128M`).

## Запуск и проверка

### 1. Сборка и запуск сервисов

```bash
mkdir -p inbox
docker compose up -d --build
docker compose ps
```

### 2. Генерация тестовых файлов и просмотр логов

```bash
for i in $(seq 1 12); do yes "2026-11-22 info service=node_$i status=ok msg=request_processed" | head -n 40000 > inbox/server_$i.log; done
docker compose logs controller
```

### 3. Проверка обработанных файлов на общем томе

```bash
docker compose exec controller ls -lh /data/out
docker compose exec controller head -n 3 /data/out/server_1.log
```

### 4. Горизонтальное масштабирование

Увеличение числа реплик воркера без остановки брокера и контроллера:

```bash
docker compose up -d --scale worker=5
sleep 2
for i in $(seq 13 27); do yes "2026-11-22 info service=node_$i status=ok msg=request_processed" | head -n 40000 > inbox/server_$i.log; done
```

Проверка распределения задач по репликам:

```bash
docker compose logs controller | grep '[DONE]' | awk '{print $4}' | sort | uniq -c
```

Проверка лимитов ресурсов (`cgroups`) и `PID 1`:

```bash
docker stats --no-stream
docker compose exec controller ps -ef
```

### 5. Остановка и очистка

```bash
docker compose down -v
rm -f inbox/*.log
```
